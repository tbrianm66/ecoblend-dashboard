You are acting as a senior full-stack product engineer, product strategist, and venture studio systems architect.

I am building **EcoBLEND IO**, a Venture Validation OS used by **EcoRACE Studio** to create, validate, and manage a portfolio of ventures using Lean Startup methodology, evidence scoring, venture readiness, and stage-gate decision-making.

The current application has a sidebar module:

**B. Venture Intake**

Your task is to audit the existing Venture Intake module and update or add the required sub-sections based on Lean Startup methodology and the wider EcoBLEND IO workflow.

The Venture Intake module must become the **front-end hypothesis capture and assumption-definition layer** for the entire system.

Its purpose is to stop ventures entering product development before the core assumptions have been made explicit, structured, and ready for testing.

The module should answer:

**“What do we believe, why do we believe it, what is the riskiest assumption, and what must we test first?”**

# 6. Sub-Section: Founder Assumptions

## Purpose

This sub-section captures what the founder believes to be true before evidence exists.

This is critical because early ventures often fail when assumptions are hidden or treated as facts.

## Required UI

Create an assumptions table and form.

Fields:

* Venture
* Assumption title
* Assumption statement
* Assumption category
* Importance score: 1–5
* Uncertainty score: 1–5
* Evidence exists: yes/no
* Evidence summary
* Risk level

## Scoring Logic

Calculate Assumption Risk Score:

Assumption Risk Score = Importance Score × Uncertainty Score

Interpretation:

* 1–5 = Low
* 6–10 = Medium
* 11–18 = High
* 19–25 = Critical

If Evidence Exists = no and Assumption Risk Score is above 15, flag as a high-risk untested assumption.

## Required Output

Show:

* Total assumptions
* High-risk assumptions
* Critical assumptions
* Assumptions without evidence
* Top 5 assumptions to test

## Auto-Generation

Allow user to convert an assumption into:

* Customer segment hypothesis
* Problem hypothesis
* Value proposition hypothesis
* Business model hypothesis
* Riskiest assumption record
* Lean experiment proposal

# 13. Sub-Section: Intake Decision

## Purpose

This sub-section decides whether the venture should proceed to validation.

It should not approve ventures based only on enthusiasm.

## Required UI

Create Intake Decision page with:

* Venture selector
* Readiness scorecard
* Assumption risk summary
* Evidence gap summary
* Recommended first experiment
* Recommended next module
* Decision form
* Approval status

## Intake Readiness Score

Calculate:

Intake Readiness Score =
Idea Completeness × 15%

* Segment Clarity × 15%
* Problem Definition × 20%
* Value Proposition Quality × 15%
* Business Model Readiness × 10%
* Lean Canvas Completeness × 10%
* Riskiest Assumption Defined × 15%

Output categories:

* 0–39 = Not ready
* 40–59 = Needs more definition
* 60–79 = Ready for initial discovery
* 80–100 = Strong intake package

## Decision Logic

If Intake Readiness Score is below 40:

* Recommend: reject, archive, or redefine idea

If 40–59:

* Recommend: research more and complete missing hypotheses

If 60–79:

* Recommend: begin customer discovery

If 80–100:

* Recommend: proceed to Discovery & Market and create first experiment

If critical assumptions exist with no test defined:

* Override recommendation: define riskiest assumption test first

## Decision Options

Allow reviewer to choose:

* Reject
* Archive
* Research more
* Begin customer discovery
* Begin market discovery
* Create first experiment
* Pivot before discovery
* Proceed to Discovery & Market

## Required Integration

When an Intake Decision is approved:

* Update venture status
* Update venture current_stage
* Create a lean_decision record if that table exists
* Create a command_alert if action is required
* Push first experiment to Experiment Queue if created
* Make the venture visible in Command Centre

# 20. Critical Failure Modes to Avoid

Avoid these mistakes:

1. **Creating another static intake form**
   Venture Intake must be a hypothesis-definition workflow, not a generic idea submission form.

2. **Confusing assumptions with evidence**
   Founder beliefs must be labelled as assumptions until tested.

3. **Allowing vague hypotheses**
   Customer, problem, value proposition, and business model hypotheses must have test methods and success metrics.

4. **Skipping the riskiest assumption**
   The system must identify what could kill the venture fastest.

5. **Disconnected module logic**
   Intake data must feed Command Centre, Discovery & Market, Proposition & Model, and R&D Hub.

6. **Duplicate venture records**
   Reuse the existing venture model where available.

7. **Premature validation**
   Intake should not mark ventures as validated. It should mark them as ready or not ready for testing.

8. **No stage-gate consequence**
   Approved intake decisions must update venture stage and status.
