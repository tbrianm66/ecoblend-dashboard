==================================================
PART A — FIRST PRODUCE THE STAGE 1 IMPLEMENTATION PLAN
==================================================

Before making structural changes, inspect the existing implementation and identify which existing objects should become authoritative for:

1. Venture identity
2. Hypothesis / assumption
3. Evidence
4. Experiment
5. Experiment result
6. Human decision
7. Audit/provenance

For each target concept classify the existing implementation as:

REUSE AS CANONICAL
REUSE + EXTEND
ADAPT THROUGH COMPATIBILITY LAYER
DO NOT USE
NEW OBJECT REQUIRED

Explicitly identify duplicated or competing implementations.

DO NOT automatically choose a duplicate implementation without explaining why.

Particular caution is required around:

- duplicate MRL engines
- risk models
- portfolio state
- readiness outputs
- permissions
- reports
- legacy versus V2 state.

==================================================
PART B — DEFINE THE VALIDATION LIFECYCLE OWNER
==================================================

Create or designate ONE authoritative Phase 1 lifecycle record.

Its purpose is to represent one validation journey for one venture.

It should connect:

VENTURE
→ VALIDATION LIFECYCLE
→ HYPOTHESES
→ EVIDENCE
→ EXPERIMENTS
→ RESULTS
→ HUMAN DECISIONS

Do not make the lifecycle record a replacement for the venture.

A venture may eventually have multiple validation cycles or versions.

The lifecycle must support at minimum:

- unique identity
- venture relationship
- lifecycle/version number
- current lifecycle state
- created date
- updated date
- created by
- ownership
- status
- auditability.

Initial lifecycle states may include:

DISCOVERY
VALIDATION
ITERATION
REVIEW
HOLD
TERMINATED
EXECUTION_READY

Do NOT implement formal G0-G6 validation gates yet.

==================================================
PART C — CANONICAL HYPOTHESIS SEMANTICS
==================================================

Stage 0 found that hypotheses/assumptions already exist in multiple forms.

Do not create another competing hypothesis system unless technically unavoidable.

Establish a canonical hypothesis identity and versioning contract.

Every canonical hypothesis should ultimately be capable of recording:

- venture
- validation lifecycle
- statement
- category
- importance
- confidence
- status
- version
- previous version where applicable
- assumptions/dependencies
- supporting evidence
- contradicting evidence
- experiments
- validation criteria
- created by
- timestamps.

If the existing structure can support this through extension or adapters, prefer that approach.

Historical records must remain valid.

==================================================
PART D — SHARED EVIDENCE CONTRACT
==================================================

Create a shared evidence contract that existing ECOBLEND modules can later consume.

Evidence must support:

- venture
- lifecycle
- linked hypothesis where appropriate
- evidence category
- source
- source reference
- collector/origin
- collection date
- provenance
- reliability
- confidence
- independence
- supports / contradicts / neutral.

Prepare the schema for the future E0-E6 evidence hierarchy but do not rewrite all historical evidence during Stage 1.

The future evidence hierarchy will distinguish:

E0 agent inference
E1 simulation
E2 secondary evidence
E3 primary qualitative evidence
E4 behavioural evidence
E5 commercial evidence
E6 operating evidence.

Do not assign high evidence classes to existing records unless provenance supports the classification.

==================================================
PART E — EXPERIMENT CONNECTION
==================================================

Reuse or adapt the existing experiment capability.

A canonical experiment must be capable of connecting:

HYPOTHESIS
→ EXPERIMENT
→ RESULT
→ EVIDENCE
→ UPDATED HYPOTHESIS STATE.

Do not build the Next Best Experiment engine yet.

==================================================
PART F — HUMAN DECISION RECORD
==================================================

Stage 0 identified that ECOBLEND does not yet have one universal human decision record.

Implement or designate a canonical Decision Record supporting:

SYSTEM RECOMMENDATION

and separately:

HUMAN DECISION.

Initial decision vocabulary:

PROCEED
ITERATE
HOLD
STOP
ESCALATE.

The system recommendation must never overwrite the human decision.

Record:

- venture
- lifecycle
- recommendation
- human decision
- decision authority
- rationale
- supporting evidence references
- date
- overrides/exceptions.

Do NOT implement automatic gate progression.

==================================================
PART H — SECURITY AND DATA SAFETY
==================================================

All new Stage 1 functionality must be venture-scoped.

Review object-level authorisation for every new read/write path.

Do not rely solely on numeric IDs supplied by the client.

Preserve existing authentication.

Do not expose previously private venture information.

Database changes must be:

ADDITIVE
NON-DESTRUCTIVE
BACKWARDS COMPATIBLE.

No table deletions.

No table renames unless separately authorised.

No destructive data conversions.

No production-data migration without explicit approval.

Confirm development and production database separation before performing structural migration.

If environment isolation cannot be verified:

STOP and report the issue rather than continuing.
