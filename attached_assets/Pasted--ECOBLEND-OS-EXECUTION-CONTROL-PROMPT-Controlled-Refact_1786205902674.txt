# ECOBLEND OS — EXECUTION CONTROL PROMPT

## Controlled Refactor and Migration Instructions

This is a master architecture specification for a significant ECOBLEND OS refactor.

DO NOT attempt to implement the entire specification in a single autonomous coding pass.

Use the full architecture specification that follows this instruction as the target-state design, but execute the work in controlled phases.

The purpose of this execution control is to minimise:

* data-loss risk
* regression risk
* schema corruption
* duplicate architecture
* broken module dependencies
* incorrect migration of existing ventures
* accidental conflation of Domain Brands, Ventures and Products

Do not make destructive changes without first understanding the existing architecture.

# REQUIRED REGRESSION TESTS

Before declaring completion, test:

### Test A — Unassigned Venture

A Venture Candidate can exist without a Domain Brand.

### Test B — Domain Brand Independence

Killing a Venture Candidate does not kill or alter its Domain Brand.

### Test C — Venture Evidence Preservation

Productisation does not overwrite or remove original Venture evidence.

### Test D — Multiple Products

One Venture may produce multiple Product Programmes.

### Test E — Brand Reassignment

Changing a Venture's Domain Brand preserves assignment history.

### Test F — Part Number Integrity

Duplicate Part Numbers cannot be created.

### Test G — Revision Integrity

Revision changes do not overwrite prior revisions.

### Test H — Backward Traceability

A Product/Part Number can trace back to:

```text
Product
→ Product Family
→ Product Programme
→ Venture Candidate
→ Evidence
→ Governance Decision
```

### Test I — Existing ECOBLEND Modules

Existing validated functionality remains operational.
